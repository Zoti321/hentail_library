# 桌面参考布局拆解：design-system/example.png

> 性质：**用户偏好参考**（用户原话：「这张图片中的布局很符合应用桌面端的需求」），不是官方规范。
> 本文把「用户偏好」与「Material 3 官方规范」分列，冲突处以用户偏好为准并标注。
> 证据等级：**B**（按像素反推的官方产品截图）+ **A**（本文比对用到的 M3 官方数值）。所有 dp 换算与密度数字均为 B 级实测。

---

## 0. 结论摘要

1. 这张图是 **Google Chat 的 Old / New 改版对照营销图**（2048×1440，绿色底）。可量的是右下 **New 窗口**：外框 1251×782 px，按 1 px = 1.152 dp 换算得 **1441×901 dp ≈ 1440×900** —— 说明它是一张按 dp 1:1 设计的 1440 宽桌面稿，缩放 0.8688 输出。
2. 它用的是 **四区并列**：顶部 app bar 72dp（全宽） + rail **80** + 导航列表 **296** + 主内容 **632** + 支撑面板 **412**。占内容宽比 **5.5% / 20.7% / 44.5% / 29.2%**。
3. **80 与 412 都不是随手取的**：80 = M3 collapsed navigation rail 宽（A），412 = M3 large/XL 支持面板固定宽（A）。参考图在「large 档 1440」上给出的正是 M3 官方值 —— 这比它像不像 Google 产品更有说服力。
4. 模式判定：**list-detail + supporting pane 的混合体**。内容栏只有 2 个（主内容 + 支撑），落在官方 large 档「1 or 2 (recommended)」（A）；导航列表 + rail 属导航面，不计入内容栏。**与 07 文档的担忧不冲突**：列表是导航面，不是「详情栏」。
5. 分隔手法：**纯 tone 级差，没有任何 1dp 分隔线**（实测 x=836 与 x=1091 边界都是直接跳色）。级差 **ΔL\* 7.05（rail→列表）与 3.83（列表→主内容）**，与 `08-tone-based-surfaces.md` 选定方案的 7.0 / 4.0 几乎重合。**这是 08 方案的最强外部旁证。**
6. 采纳结论：**采纳比例与分隔逻辑，不采纳其密度与无 margin 的全出血形态**（详见 §6）。

## 3. 四个维度拆解

### 3.1 栏数与栏宽比例

- **5 个纵向条带，4 种宽度**：app bar（全宽，横跨 rail 以外）→ rail 80 → 列表 296 → 主内容 632 → 支撑 412。
- 主内容 : 支撑 = **632 : 412 ≈ 1.53 : 1**。支撑栏取官方 412 后，主内容仍保持绝对主导（>44%）。
- 列表 296 只有主内容的 **47%**，明显小于「列表 : 详情 = 1 : 2」的经典双栏比。原因见 3.2：它是**纯文本二级导航**，不是带封面的内容列表。
- **对我们最要紧的一条**：`41:2384` 的列表 504 与 rail 256 合计 760 dp，占 1920 的 40%；参考图同位置只用了 80 + 296 = 376 dp（占 1440 的 26%）。**横向预算浪费是我们模板最实际的毛病。**

### 3.2 导航形态

- rail 是 **M3 collapsed（standard）rail 80**：图标在上、**标签在下**（实测 x=772..834 的暗色行程：669–681 图标 + 696–704 标签、731–745 + 760–768、796–808 + 823–833、860–872 + 887–895，**item 间距 62/65/64 px → 72–75 dp**）。
  → 纠正一个容易犯的误判：它**不是**「收成纯图标的 icon rail」，而是「带标签的窄 rail」。M3 的 collapsed rail 本来就是图标 + 标签（A）。
- **列表是二级导航面，不是内容栏**：Chats / Spaces 两组，条目为「图标 + 名称」的纯文本行，**没有缩略图、没有摘要卡**。
- **结论（本文件最重要的一条工程判断，C 级但有 B 级锚点）**：
  > **rail 的宽度是「同屏栏数」的函数，不只是断点的函数。**
  > 屏幕上已经有 3 个内容区时，rail 必须退到 collapsed 80；只有栏数 ≤2 时才用 expanded 256 换可读性。
  参考图右侧 3 栏全开时选 80；`41:2384` 同样 3 栏却选 256 —— 这是它视觉发挤、主内容被挤到 504 以下的直接原因。

### 3.3 内容密度（dp）

| 元素 | 实测 | 说明 |
|---|---|---|
| app bar 高 | **72** | 62 px |
| 搜索框高 | **52** | 45 px，白色 `#FFFFFF` 浮在 `#EDEFE5` 上（唯一用纯白抬高的元素） |
| 列表行距 | **38**（33 px） | 单行主信息 + 次要行，属高密度紧凑列表 |
| rail item 间距 | **72–75** | 图标 + 标签两行 |
| 日历小时行距 | **50**（43–44 px） | 时间轴行：`#F3F5EB` 卡片内时间标签 9–10 dp 高 |
| 支撑面板 mini 图标条 | **64** 宽 | 面板内再嵌一条工具列（日历 / 任务 / 新建 / info / pin） |
| 主 CTA 药丸高 | **62** | ≥48 dp 目标（A 级可访问性要求）满足 |

**密度结论**：桌面档的行距明显低于移动档（我们移动端列表行 ~72–88 dp）。桌面接受 **38–50 dp 行距**，但**点击目标仍要 ≥48 dp**（A）—— 参考图用「行高 38 + 行内可点区域 48」之外的折中（Google 自己的列表行是可点的整行，行距 38 dp 其实低于 48）。**这一条我们**不**照抄**：我们的列表行保留 ≥56 dp（书库卡片更高），只在**元数据 / 设置 / 历史**这类纯文本行上采用 44–48 dp。

### 3.4 留白与分组手法

1. **无分隔线，只用 tone**：x=836（rail→列表 `#D9DBD1`→`#EDEFE5`）与 x=1091（列表→主内容 `#EDEFE5`→`#F8FAF0`）都是**直接跳色，没有任何 1 px 深色线**（实测像素序列见 §2.1，边界仅 1 px 抗锯齿）。
2. **级差分两档**：并列 zone 之间用大级差（7.0 / 4.0），**zone 内部**用极小的级差（列表→卡片 1.7–2.1）—— 与 `08` 文档「大级差给并列面板、小级差给卡片」的判断完全一致。
3. **零 margin 全出血**：面板与面板直接相接，不做 24 dp 内缩。这让 1440 宽下的信息量最大化，代价是「悬浮卡片感」消失、变成「窗口分区感」。
4. **只有一处用白色抬高**：搜索框 `#FFFFFF`（tone 100）—— 对照我们 `surfaceContainerLowest #FFFFFF`（A 板 tone 100），用法一致。
5. **面板内 padding 约 20–24 dp**（列表内容 x 从 855 起，面板起 836，差 19 px ≈ 22 dp），与 M3 的 24 dp（A）同级。
6. **CTA 用品牌色实心**（`#B8F397`，tone 90），位置在 app bar 下方左对齐，不在 app bar 里 —— 与 M3「FAB 不进 app bar」一致。

## 4. 模式判定

| 判据（取自 `07-supporting-pane.md` §2 的四问） | 参考图 |
|---|---|
| 有几个**内容**栏？ | **2**（主内容 + 支撑）；rail 与列表是导航面 |
| 支撑内容是否属「同一对象的切面」？ | 是（日历 / 任务 辅助当前会话）——语义上是 companion（伴随工具），形态上是 supporting pane |
| 列表与主内容是否父子？ | 是（Chats 列表 → 会话详情）⇒ **list-detail** |
| 是否有第三个内容栏？ | 无；官方 XL「1 to 3 (recommended)」（A）未用满 |

**判定：list-detail + supporting pane 的混合体**，具体形态为

```
[ rail 80 (nav) ] [ 列表 296 (nav, list-detail 的 list) ] [ 主内容 632 (detail) ] [ 支撑 412 (supporting pane) ]
                   ↑ 父子关系：换对象                                     ↑ 换视角：同一对象的伴随信息
```

- 与 **07 文档的冲突点可以消解**：07 担心「`41:2384` 画列表 + 详情同屏，而代码里详情是独立路由」。参考图说明「列表 = 导航面」可以**常驻**，代价是详情必须**内联**（同路由换 pane），而不是推新路由。这仍是一个**产品决策**（见 §9 未决项 1），但参考图给出了一个官方产品级先例。
- 与 **08 文档的分隔方案一致**：这正是「同级差给并列、无分隔线」的用法。

## 6. 采纳结论

### 6.1 用户偏好（用户明确说过「很符合桌面端需求」→ 优先采纳）

| # | 采纳项 | 落到哪 |
|---|---|---|
| 1 | **rail 用 collapsed 80**（图标 + 标签），不用 expanded 256 —— 只要同屏 ≥3 栏 | `MASTER §5.1` large/XL 行、`41:2384` |
| 2 | **支撑栏 412**（large/XL）/ **360**（expanded） | `MASTER §5.1`、`07` §4.1、新模板帧 |
| 3 | **纯 tone 分隔，不加分隔线**（级差 7.0 / 4.0 足够） | `MASTER §2.3` + `08` 方案 1（互相印证） |
| 4 | **面板全出血**（pane 之间 0 margin）+ pane 内 24 dp padding | 新模板帧 |
| 5 | 导航列表 **296 / 320**（纯文本二级导航） | 新模板帧、`08 Screens` |
| 6 | 支撑面板内可嵌 **64 dp** 工具条 | 阅读器浮层（`07` 已建议「可召唤浮层」） |

### 6.2 官方规范 / 我们的既有规则（冲突处让步，但保留理由）

| 项 | 官方或现状 | 参考图 | 处理 |
|---|---|---|---|
| pane 间 margin | M3 canonical 24 dp（A） | 0（全出血） | **站官方侧**：详情模板一律取 24 dp（pane 间与右缘），不照搬参考图的 0 margin——参考图是产品取舍，不是规范 |
| 列表行高 | 点击目标 ≥48 dp（A） | 行距 38 dp | **不采纳**：我们列表行 ≥56 dp；仅元数据/设置/历史纯文本行降到 44–48 dp |
| 书库列表宽 | — | 296（无封面） | **不采纳 296**：书库列表带 220 dp 封面（`detail_primary_row_layout.dart:11`）+ 12 dp padding ⇒ **≥360** |
| 阴影分区 | tonal，不用阴影 | 不用阴影 | 一致，维持 `08` 方案 3（阴影只给浮层） |

### 6.3 一句话结论（最终采纳口径，2026-10-23）

> **采纳它的「纯 tone 分隔 + 三区级差（87 / 94 / 98）+ rail 80 + 支撑 412」，不采纳它的「rail 带文字标签的分类导航」「38 dp 行距 / 296 宽内容列表」「0 margin 全出血」。**

本文最初建议的 **rail 80 + 列表 320** 四栏组合**已作废**：用户决定书库不走 inline list-detail（详情是独立路由），模板改造后各档都是三栏「rail + 详情 + 支撑」。因此参考图对我们的实际贡献是：

| 参考图特征 | 落点 | 状态 |
|---|---|---|
| rail 视觉宽 80（近图标列，非 256） | large 详情页的 rail | ✅ 采用 |
| 支撑栏 412（≈360 的 1.144×） | large/XL 支撑栏（官方亦为 412） | ✅ 采用 |
| 纯 tone 分区、零分隔线 | 三区映射（87 / 94 / 98） | ✅ 采用（`08` §4.1） |
| pane 内 24 padding | 三个详情模板 | ✅ 采用 |
| 0 margin 全出血 | — | ❌ 不采用：模板 pane 间与右缘保留 24 画布底（更接近官方 canonical，且用户要求留白） |
| 面板内 64 dp 工具条 | 阅读器浮层工具栏 | ✅ 采用（`07` 已建议浮层） |
| 导航列表 296 + 行距 38 | — | ❌ 不采用（无 inline list-detail） |

`08` 的桌面三区映射与参考图互相印证：rail→列表 ΔL\* 7.05、列表→内容 3.83，正对应我们取的 **7.0 / 4.0**。

## 10. 来源与方法

**来源（全部 B 级，单一图片）：**

- `design-system/example.png`（2048×1440，用户既有文件；我只读取、未修改，最终由用户自己在 `854dc1d3` 提交入库）
- 官方数值（A，用于对照）：`MASTER §5.1`（rail 80 / 256）、`07-supporting-pane.md` §4.1（expanded 360 / large·XL 412）、`08-tone-based-surfaces.md` §2（tone 分配到 hex + ΔL\*）

**方法（可复现，B 级）：**

1. Pillow 逐行/逐列扫纯色带，定位 pane 边界（`px[x,y]` 连续相同即一带）。
2. 以「内容区高 782 px ↔ 900 dp」与「外框宽 1251 px ↔ 1440 dp」两式互校，得 1 px = 1.152 dp（误差 < 0.1%）。
3. 边界处逐像素打印，确认**是否存在 1 px 分隔线**（结论：不存在，仅 1 px 抗锯齿）。
4. tone 由 sRGB → CIELAB（D65，白点 0.95047/1/1.08883）直接算 `L*`，与 `08` 同一口径。

> 局限：这是一张**营销渲染图**，不是可交互原型，也不是 Figma 源文件。它证明的是「Google 的桌面产品长这样」，不能证明「用户就想要这个」。**用户偏好来自用户对该图的一句话判断，不来自这张图本身。**
